# Catalog Video — Upload-Your-Own-Image Source — Design

## Scope

Add a second source option to the "New Catalog Video" wizard
(`apps/catalogues-web/src/app/(app)/catalog-video/CatalogVideoWizard.tsx`).
Today step 1 only lets the user pick from their own completed AI Vastra
catalogue images (a `sourceJobId`). This adds an "Upload New" tab that lets
the user upload an arbitrary image of their choice — not required to have
been generated by AI Vastra at all — and use it as the animation source
instead.

Out of scope (explicitly decided during brainstorming):
- The uploaded image must already be a "ready" model/garment photo, framed
  for animation as-is. It is sent straight to PixVerse; no try-on generation
  (face/pose/background selection) runs on it first.
- The uploaded image is a one-time input to a single video job only. It is
  never saved as a catalogue/job entry and never appears in Catalogues or My
  Products.

## Problem

`POST /v1/jobs/catalog-video` (`createCatalogVideoJob` in
`apps/api/src/modules/jobs/create.ts`) requires `sourceJobId`: a job the
caller owns that is `COMPLETED`. This means every catalog video must trace
back to a prior AI Vastra generation. Users who already have a suitable photo
from outside AI Vastra (an older shoot, a photo they own the rights to) have
no way to animate it without first re-creating it inside AI Vastra, which may
not even be possible (e.g. no matching Studio inputs).

## Design

### 1. Request contract — `packages/types/src/jobs.ts`

`CreateCatalogVideoJobRequest` changes from requiring `sourceJobId` to
requiring **exactly one of**:

```ts
export const CreateCatalogVideoJobRequest = z
  .object({
    sourceJobId: z.string().uuid().optional(),
    sourceImageKey: z.string().regex(INPUT_GARMENT_KEY).optional(),
    sampleVideoId: z.string().uuid(),
  })
  .refine((d) => Boolean(d.sourceJobId) !== Boolean(d.sourceImageKey), {
    message: 'Provide either sourceJobId or sourceImageKey, not both',
  });
```

This mirrors the existing `upperGarmentKey` / `mannequinJobId` XOR pattern on
`CreateTryOnJobInputs` (same file) — same shape, same enforcement style.

### 2. Upload mechanics — no new endpoint

The wizard uploads through the existing `POST /v1/uploads/presign` (used
today by Studio's garment upload): request a presigned PUT URL + `r2Key`,
`PUT` the file straight to R2 client-side via `api.uploadToR2WithProgress`,
done. The presign route already binds the issued key to the caller in Redis
for 24h (`upload:owner:{r2Key}` → `userId`) — no new ownership mechanism
needed.

### 3. Backend — `createCatalogVideoJob`

Branch once, at the top of the function, on which field is present:

```ts
let resolvedSourceImageKey: string;
if (body.sourceImageKey) {
  await assertOwnsUploadKey(app, userId, body.sourceImageKey);
  resolvedSourceImageKey = body.sourceImageKey;
} else {
  // existing sourceJobId lookup: ownership + COMPLETED check, resolve resultKey
  ...
  resolvedSourceImageKey = source.resultKey ?? keys.output(body.sourceJobId);
}
```

`assertOwnsUploadKey` (`apps/api/src/lib/upload-ownership.ts`) already does
two checks, not one: the Redis ownership binding, *and* a `headObject` R2
existence/size check via `assertGarmentObjectValid`. Both failure modes
(key not owned/expired, object never actually landed in R2) are caught here,
before any credit deduction.

Everything after this branch is unchanged and shared by both paths: credit
cost lookup (`getPixverseCreditCost`), the `isCatalogVideoAllowed` allowlist
gate, the banned-user check, writing `job_inputs.params.sourceImageKey =
resolvedSourceImageKey`, the `jobs:video` XADD, and refund-on-enqueue-failure.
The dispatcher (`processVideoJob` in `apps/dispatcher/src/job/processor.ts`)
needs no changes — it already just reads `sourceImageKey` out of
`job_inputs.params` with no notion of where it came from.

### 4. Frontend — `CatalogVideoWizard.tsx`

**Step 1** gains a tab/toggle above the existing grid:
**"My Catalogue Images"** | **"Upload New"**.

- *My Catalogue Images*: unchanged — today's grid of completed-job thumbnails
  (fetched per-job via `/v1/jobs/:id/thumbnail`, per the fix already shipped
  for the duplicate-thumbnail bug).
- *Upload New*: a dropzone (click-to-browse or drag-and-drop), mirroring
  Studio's `handleGarmentUpload` exactly:
  - Client-side validation: magic-byte check for JPEG/PNG/WebP, 10MB soft
    cap (server hard-caps at 20MB via `PresignUploadBody` regardless — same
    pairing Studio already uses successfully).
  - Immediate local preview via `URL.createObjectURL(file)` — no round trip
    needed to show what was picked.
  - Presign → upload to R2 with a progress bar (`api.uploadToR2WithProgress`),
    same as Studio.
  - Success sets the uploaded key as the selected source; `Next` unlocks,
    same as picking a grid tile does today.
  - In-flight upload is aborted (`AbortController`, per-attempt ref) if the
    wizard is closed or the user switches back to the other tab mid-upload.

**State model**: replace the current `sourceJobId: string | null` with a
tagged union so step 3 (and submit) know which kind of source is selected:

```ts
type ImageSource =
  | { kind: 'existing'; jobId: string }
  | { kind: 'upload'; r2Key: string; previewUrl: string };
```

Step 3's preview panel renders `previewUrl` directly (local blob URL, no
fetch) for the upload case, and the existing `JobThumbnail` component
(`/v1/jobs/:id/thumbnail`) for the existing-image case. Submit posts either
`{ sourceJobId, sampleVideoId }` or `{ sourceImageKey, sampleVideoId }`
depending on `ImageSource.kind`.

### 5. Error handling

| Case | Where | User-facing behavior |
|---|---|---|
| Bad file type / >10MB | Client, before upload | Toast, upload never attempted |
| Wizard closed / tab switched mid-upload | Client | Upload aborted via `AbortController` |
| Presign or R2 PUT fails | Client | Toast: "Upload failed: ..." |
| `403 FORBIDDEN` — key not owned / 24h binding expired | Server (`assertOwnsUploadKey`) | "Upload session expired — please re-upload your image and try again." |
| `400 BAD_UPLOAD` — R2 object missing | Server (`assertGarmentObjectValid`) | "We couldn't find that upload — please try again." |
| `413 BAD_UPLOAD` — exceeds server size limit | Server | Generic upload-failed toast (unreachable in practice given the 10MB client cap) |
| Insufficient credits / `isCatalogVideoAllowed` gate | Server | **Unchanged** — identical for both source kinds |
| PixVerse failure after dispatch | Dispatcher | **Unchanged** — dispatcher has no notion of source origin |

### 6. Testing

- `packages/types`: unit test the new XOR `.refine()` — rejects
  both-present and neither-present, accepts either alone.
- `apps/api` integration tests (existing docker-compose-backed harness):
  - `createCatalogVideoJob` with an owned `sourceImageKey` → succeeds,
    `job_inputs.params.sourceImageKey` set, credits deducted.
  - `createCatalogVideoJob` with a `sourceImageKey` not owned by caller →
    403.
  - `createCatalogVideoJob` with a `sourceImageKey` whose R2 object doesn't
    exist → 400.
  - Existing `sourceJobId` path still passes unchanged (regression).
- Frontend: manual verification in-browser (upload flow, tab switching,
  preview, submit, credit-cost display, error toasts). `apps/catalogues-web`
  has no frontend test runner configured today, so this stays consistent
  with the rest of that app.
